# 11-01 시각 변경 누락·11-07~11-10 운영 중단 — 피해와 복구 (2026-11-11)

- 2026-11-11 사용자 지시 "[11-01 시각 변경 누락 / 복구]"에 따른 보고다.
- 코드는 바꾸지 않았다. 지난 날짜에는 배당 입력, 소급 평가, 보충 실행을 하지 않는다.

## 구간 (2026-11-11 사용자 정정에 따라 둘로 나눔)
- **시각 오류 구간 — ET 경기일 11-01~11-06**
  - A·B 예약이 KST 06:50·09:50 그대로여서, 정해진 시각보다 1시간 일찍(16:50·19:50 EST) 돌았다. A·B 예측은 모두 예비다.
  - C는 시각이 맞았다(21:50 KST = 07:50 EST).
- **운영 중단 구간 — ET 경기일 11-07~11-10**
  - 11-07 A부터 11-10 C까지 실행이 없거나 실패했다.
  - 원인은 사용자의 구독 결제 일시 중단이다(2026-11-11 사용자 전달).
  - 그 앞뒤로 11-07 C는 정상으로 돌았다. 11-10 A·B는 돌았지만 여전히 1시간 이른 시각이었다(시각 오류).
- **두 구간 공통**
  - 평가하지 않는다("평가 안 함").
  - 배당 소급 입력, 소급 평가, 소급 픽, 지난 예측 사후 생성은 하지 않는다.
  - 해제 조건 집계에 들어가는 것도 없다(평가 레코드 0건).
- **끝(2026-11-12 확인):** 사용자가 A 07:50, B 10:50 KST로 바꿨다(11-11 08:03Z).
  - 11-11 ET 실행 A는 22:52Z(17:52 EST)에 시작했다. 최종 7, 예비 3이고, 예비 3은 B 그룹이다.
  - 실행 B는 01:51Z(20:51 EST)에 시작했다. 10경기 모두 최종이다.
  - 그래서 정상 구간은 11-11 ET부터다. 시각 오류는 11-10 ET 실행 B(11-11 00:51Z)가 마지막이다.

## 자동 경고 계획 (구현하지 않음, 승인 뒤 구현)
1. **`runEarly`(기준 시각 전 실행)**
   - 내용: `prepare A|B`에서 시작 시각이 `runAt(run, date)`보다 일찍이면 경고를 남긴다. 5~90분 이르고, 대상 경기가 모두 예비인 경우다.
   - 연속 처리: 2회 연속(직전 실행과 비교)이면 기존 승격 방식(`engine/run-alerts.js` ESCALATE)으로 `escalated`가 붙는다. 대시보드 머리글에 "연속 경고" 칩이 뜨고, `push`에 문장이 들어간다.
     - 예: "실행 A가 기준 시각(17:50 ET)보다 60분 일찍 돌았습니다. 예약 시각을 확인하세요(서머타임)"
   - 수동 실행: 따로 표시하는 인자(`--manual`)를 받으면 제외한다.
2. **`missedRun`(빠진 실행)**
   - 내용: 실행마다 직전 예정 실행(A·B·C)의 실행 기록이 main에 있는지 본다. 없으면 경고하고, 1회부터 푸시한다.
   - 11-07~11-10 공백은 11-10 A에서 잡혔을 것이다.
3. **`finalZero`(최종 0 연속)**
   - 내용: 경기가 있는 날 A·B의 최종 예측이 0인 날이 2일 연속이면 경고·승격·푸시를 낸다. 대시보드 상단에도 "시각 오류 의심"을 띄운다.
4. **`evalZero`(평가 0 연속)**
   - 내용: 배당 입력이 있는데 평가가 0건인 날이 2일 연속이면 같은 방식으로 경고한다. 입력이 없는 날은 세지 않는다.
5. **지시문:** A·B 지시문에 `push` 전송 줄을 넣는다. 이번 11-01용 블록에 이미 있다.
6. **서머타임 경계 테스트:** 11-01·03-14 앞뒤의 예약 시각 조합(바꿈/안 바꿈)으로 1~3이 맞게 뜨는지 시험한다.

- 영향: 바꾸는 파일은 `jobs/daily.js`, `engine/run-alerts.js`, 대시보드 경고 문구, 테스트다. 모두 동결 파일 밖이다. 예측과 평가 규칙은 바꾸지 않는다.
- 위 기준값(5~90분, 2일 연속)은 제안이다. 승인 때 정한다.

### 오류 기록과 결제 중단 설명의 대조
- **확인된 오류는 1건이다(11-10 C, 세션 `cse_01Wpwrz7gFb6fruNhMcxYbkD`).** 원문은 아래와 같다.

  - **사용자 전달로만 아는 것:** 원인이 결제 중단이라는 점이다.

## 외부 감시 계획 (구현하지 않음)
- 구독이나 예약 작업이 멈추면 그 안의 경고도 함께 멈춘다. 그래서 바깥에서 "최신 게시 시각"을 보는 장치가 필요하다.

| 안 | 무엇 | 사용자 설정 / 코드 | 멈추는 조건 |
|---|---|---|---|
| 1 | 휴대폰 달력 반복 알림. 매일 08:05·11:05·22:05 KST에 "대시보드 머리글의 게시 시각 확인" | **사용자 설정**(달력 앱) | 휴대폰이 꺼질 때만 |
| 2 | 대시보드의 "오래된 게시" 배너. 페이지를 여는 순간 브라우저가 지금 시각과 마지막 게시 시각을 비교한다. 예상 실행보다 3시간 넘게 지났으면 빨간 배너("마지막 게시 n시간 전, 예약 작업 확인") | **코드**(`dashboard/app.js`) | 없음(열 때 계산한다). 다만 사용자가 열어야 보인다 |
| 3 | GitHub Actions 정기 점검. 하루 3번 main의 최신 `data/runs` 커밋 시각을 보고, 너무 오래됐으면 저장소에 이슈를 연다. GitHub 앱이나 메일로 알림이 간다 | **코드**(`.github/workflows/`, 점검 스크립트) + **사용자 설정**(GitHub 알림 켜기) | Claude 구독과 무관. GitHub Actions 사용 한도나 저장소 설정에 따름 |
| 4 | 외부 "생존 신호" 서비스(dead-man's switch). 실행마다 신호를 보내고, 끊기면 서비스가 알린다 | **사용자 설정**(서비스 가입, 알림 경로) + **코드**(지시문에 신호 한 줄) + 네트워크 허용 호스트 추가 | 외부 서비스에 따름 |

- **권장:** 1(오늘부터, 코드 없음) + 2 + 3
  - 3은 Claude 구독과 예약 작업 바깥에서 돈다. 이번 같은 중단에도 알림이 간다.
  - 4는 외부 계정과 네트워크 허용이 필요해서 뒤로 둔다.
- 2와 3의 임계값(예: 예상 실행 + 3시간)과 점검 시각은 승인 때 정한다.
