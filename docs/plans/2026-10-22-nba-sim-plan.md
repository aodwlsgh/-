## 1. 설계와 다르게 가는 것 (승인된 것)
| # | 내용 |
|---|---|
| D1 | 코드·가공 데이터·문서는 Git 저장소, 대시보드·최신 데이터·픽 기록 DB는 아티팩트 |

### 1.1 브랜치와 병합 규칙 (D5)
- 현황(2026-10-22 확인): 원격에는 `claude/new-session-0toqi8` 하나만 있고, 이 브랜치가 기본 브랜치다. `main`은 없다.
- `main`은 P1 준비 커밋(이 계획 반영) 시점에 작업 브랜치 HEAD로 만든다. 같은 이력이고 새 커밋은 없다. 그 뒤 사용자가 GitHub Settings → Default branch를 `main`으로 바꾼다.
- 언제 합치나
  1. 단계가 끝날 때(완료 기준 통과 + 보고)
  2. 작업 세션을 끝낼 때. 다른 PC에서 바로 이어받을 수 있게 한다.
  - 두 경우 모두 `node --test`가 전부 통과하는 상태여야 한다. 테스트가 깨진 중간 상태는 작업 브랜치에만 둔다.
- 어떻게 합치나
  - `git push origin HEAD:main`으로 **fast-forward만** 한다. 강제 푸시와 이력 재작성은 금지한다.
  - `main`이 앞서 있으면(다른 PC 세션이 먼저 합친 경우) 작업 브랜치에 `main`을 먼저 merge하고 테스트한 뒤 합친다.
- 이어받기
  - 새 세션은 `main`에서 시작한다. 처음에 `docs/STATUS.md`(현재 단계, 다음 할 일, 미해결 결정)를 읽는다.
  - 합칠 때마다 STATUS를 갱신한다.

- 외부 의존성: `pdfjs-dist`만 쓴다(NBA PDF, Node 전용). 난수·분포·회귀는 직접 구현한다.
- 스키마 규칙(구현 완료)
  - 모든 ESPN 응답은 `assertValid()`로 검사한다. 어긋나면 `SchemaError`로 중단한다.
  - 데이터 결함은 `checkSummaryQuality()`로 경기별 품질 경고를 붙이고 대체 규칙으로 처리한다. 리포트에 표시하며, 조용히 넘어가지 않는다.

  - 초당 2회 이하, 지수 백오프 최대 3회
  - 프록시 터널 거부(403 CONNECT)나 Akamai 403은 재시도하지 않고 도메인을 명시해 중단한다.

### P7 마켓·픽 엔진 (2026-10-23 사용자 조건 반영 — 구현 전 계획 보고)
- **원칙**
  - 새 모듈만 추가한다. 예측 코드·파라미터·회귀 테스트(53c88f5 해시)는 그대로이고, 깨지는 변경은 먼저 보고한다.

- **`engine/markets.js` — 기본 예측에서 베트맨 기준선의 확률을 직접 계산한다**(조건 6)
  - 입력: 기본 시뮬레이션 요약 + 앙상블 이동량 + 보정층(`calibration.json`). 계산은 `engine/calibrate.js`의 `markets()`를 그대로 쓴다.
  - 승패: P(홈 승). 승5패: 홈 6점 이상 승 / 5점 이내 / 원정 6점 이상 승. 모두 연장 포함이다.
  - 핸디캡 H: P(홈 + H > 원정)을 **그 기준선에서 직접** 구한다. 표준 기준선으로 대체하지 않는다.
  - 언더오버 L: P(총점 > L)을 그 기준선에서 직접 구한다.
  - 보정 범위 밖이면 확률을 내지 않고 픽에서 뺀다(설계 §14.4.1).
    - 핸디캡: |H| > 15.5
    - 언더오버: 예상 총점에서 15점 넘게 떨어진 L
  - 기준선 형식: x.5 기준선을 지원한다. 정수 기준선(무승부·적특 가능)은 첫 실제 캡처에서 베트맨 규정을 확인하기 전까지 "미지원"으로 기록만 하고 픽에서 뺀다.

  - 함께 저장: 선택지별 단순 내재확률 1/배당, 오버라운드 Σ(1/배당), **마진 제거 시장 내재확률** (1/배당)/Σ(1/배당). 마지막 값은 §9.4 해제 조건 3(시장 대비 Brier)에 쓴다.

- **`engine/picks.js` — 픽 규칙은 그대로다**(조건 3)
  - `p_cons = p − 0.1·|p − 0.5|`(등록 공식)
  - `EV = p_cons × 배당 − 1`
  - 단일 다리 채택: EV ≥ +3%
  - 2폴더
    - 채택된 다리 2개로만 만든다. 서로 다른 경기, 같은 회차여야 한다.
    - **원배당 곱 ≥ 2.0**(베트맨 표시 반올림 전)
    - 조합 EV = p₁·p₂·o₁·o₂ − 1(보수 확률, 독립 가정)
    - 정렬: 조합 EV 내림차순, 동률이면 적중 확률 순. 상위 3개와 가장 이른 마감을 표시한다.

  - 기록용으로 `p_cons_old = 0.5 + 0.9·(p − 0.5)`와 그 EV도 함께 계산한다. 채택에는 쓰지 않는다.
  - 손익분기표(§9.3): 선택지별 최소 필요 배당 1.03/p_cons, 핸디캡·언더오버는 예상 ±3점의 x.5 기준선별 확률과 최소 배당

    - 구매 권장은 사용자 해제 기록이 있어야 켜지고, 그 기능은 지금 만들지 않는다.
    - 시장별 판정 등급은 `p5-open.json`의 결과(네 시장 통과)를 읽는다.

- **1. 누가 언제 평가·픽을 확정하나 (조건 4)**
  - **확정 조건:** 마켓의 평가·픽은 두 가지가 모두 갖춰진 첫 시점에 한 번 확정된다. 확정은 그 시점에 쓰는 쪽이 한다.
    - 그 경기의 **최종 기본 예측**이 게시되어 있다.
      - A그룹(17:50 ET 이후 ~ 21:00 ET 전 시작)은 실행 A가 최종이다.
      - B그룹(21:00 ET 이후 시작)은 실행 B가 최종이다.
    - 그 마켓의 배당이 입력되어 있다.
  - 첫 확정 뒤에 같은 마켓을 다시 입력하면 배당 레코드로만 남는다(조건 1 (A)).
  - 정해진 실행 시각보다 먼저 돈 실행(수동 실행 등)의 예측은 **"예비"(`final: false`)**로 게시하고 평가에 쓰지 않는다.
  - **쓰는 쪽은 셋이다**
    1. **대시보드** — 사용자가 배당을 입력한다.
       - 최종 예측이 있는 경기: 확인 화면 → [확정] → 그 자리에서 평가·단일 후보·2폴더를 확정한다.
       - 최종 예측이 아직 없는 경기(B그룹, 실행 B 전): 배당 레코드만 남긴다.
    2. **Claude 대화 세션** — 사용자가 있을 때 Chrome 화면이나 캡처를 판독한다.
       - 판독한 표를 보여 주고, 사용자가 확인하면 대시보드와 같은 규칙으로 기록한다.
       - 쓰기는 일일 작업과 같은 ArtifactData 경로로 한다.
    3. **일일 실행 A·B**
       - 최종 예측을 게시한 뒤, 배당 레코드만 있는 마켓을 평가·확정한다. 마감 전 마켓만 대상이다(결정 1).
       - 전날 경기 결과를 `result` 레코드로 추가한다.
  - **시각 순서**

    | ET | KST(서머타임 중, ~10-31) | KST(표준시, 11-01~) | 누가 | 무엇 |
    |---|---|---|---|---|
    | 17:50 전 | 06:50 전 | 07:50 전 | — | 대시보드에는 전날 파일이 있다. 오늘 경기는 파일에 없어서 배당을 입력할 수 없다 |
    | 17:50 | 06:50 | 07:50 | 실행 A | 수집 → 예측(A그룹 최종, B그룹 예비) → **게시** → 결과·대기 배당 쓰기 → 민감도 → 재게시 → git |
    | A 게시 후 ~ 각 마감 | | | 사용자(대시보드) 또는 Claude 세션 | A그룹: 입력 즉시 평가·픽 확정. B그룹: 배당 레코드만 |
    | 19:00 시작 경기 | 08:00 | 09:00 | — | 이 경기 마감은 베트맨 화면의 마감 시각(입력값)이다 |
    | 20:50 | 09:50 | 10:50 | 실행 B | B그룹 최종 예측 → **대기 배당 평가·쓰기(마감 전 것만)** → 게시 → 민감도 → git |
    | B 게시 후 ~ 각 마감 | | | 사용자 또는 Claude 세션 | B그룹: 입력 즉시 평가·픽 확정 |
    | 22:00 시작 경기 | 11:00 | 12:00 | — | |
  - **마감 시각**
    - 베트맨 마감 시각은 입력한 값으로만 안다. 몇 분 전에 마감하는지는 확인한 규칙이 없다.
    - 확정 시각이 마감 이후이면 기록하지 않는다(기존 `pickRecord`·배당 검증 그대로).
  - **마감 전에 확정하지 못할 수 있는 경기**(2024-25 일정 1,230경기 기준)
    - 18:00 ET 시작 55경기(4.5%): 실행 A 게시가 마감보다 늦을 수 있다.
    - 21:00 ET 시작 86경기(7.0%): 실행 B가 마감 전에 끝나지 못할 수 있다(결정 2).
    - 실제 게시 시각과 쓰기 시각을 `runs`에 남겨 측정한다. 마감을 넘긴 마켓은 "마감 경과로 평가 못 함"으로 보고한다.
  - **실행 B는 마감을 먼저 맞춘다:** B그룹 예측 → 대기 배당 평가·쓰기 → 게시 순서로 하고, 민감도·git은 그 뒤에 한다.

- **2. 배당 입력 화면 (조건 1·3·5)**
  - **확인 화면**
    - [저장]을 누르면 바로 쓰지 않고 확인 표를 띄운다. 아티팩트에서는 `confirm()`이 동작하지 않아서 화면 안에 만든다.
    - 확인 표에는 마켓별로 기준선, 배당, 오버라운드, 처리 방식을 보인다. 처리 방식은 넷 중 하나다.
      - "평가·픽 확정 — 확정 뒤 수정 불가"
      - "배당만 기록 — 이미 확정된 마켓(변동 모니터링용)"
      - "배당만 기록 — 실행 B 예측 뒤 평가"
      - "미지원(정수 기준선)"
    - 버튼은 [확정]과 [돌아가기]다.
    - 확정한 뒤와 입력 폼 머리에 "확정된 기록은 수정할 수 없습니다"를 표시한다.
  - **오버라운드 경고:** 기준 밖이면 노란 경고만 띄우고 막지 않는다. 기준은 결정 4다. 레코드는 이미 오버라운드를 저장하고 있어서, 레코드 형식은 바꾸지 않는다.
  - **배당 변동 모니터링**
    - 같은 마켓에서 첫 배당 레코드와 나중 배당 레코드를 비교한다: 선택지별 배당, 마진 제거 확률 변화(%p), 입력 시각 차이.
    - 원본 배당 레코드가 이미 체인에 있으므로 새 레코드 종류는 만들지 않고 체인에서 계산한다.
    - 기록·성적 탭과 일일 리포트에 모니터링 항목으로만 싣는다. 픽·EV에는 쓰지 않는다.
  - **"배당 미입력"과 "오늘은 패스"는 따로 표시한다(조건 5)**
    - 경기나 마켓에 배당 레코드가 없으면: 평가하지 않고 "배당 미입력"이라고 쓴다. 마감까지 없었으면 "배당 미입력(마감)"이다.
    - 배당은 있지만 최종 예측 전이면: "평가 대기(실행 B 뒤)"
    - 평가는 끝났지만 조건을 채운 다리·2폴더가 없을 때만: "오늘은 패스"
    - 그날 배당이 하나도 없으면: 하루 전체를 "배당 미입력"으로 표시한다. 지금 화면은 2폴더가 없으면 배당이 없어도 "오늘은 패스"를 띄우는데, 이것을 고친다.
  - **2폴더는 해제 조건에 넣지 않는다(조건 3)**
    - 기록·성적 탭의 "해제 조건 진행도"는 단일 픽만 계산한다.
    - 2폴더는 "2폴더 기록 — 해제 조건에 넣지 않음" 별도 표로 둔다. 값만 보이고, 목표·충족 칸은 두지 않는다.
    - 정의: 조합 확률은 두 다리 확률의 곱이고, 시장 Brier도 같은 방식이다. ROI 구간은 회차 단위 군집이다.

- **3. DB 쓰기와 실패 처리 (조건 6·7)**
  - **일일 실행의 쓰기 순서.** ArtifactData는 Claude 도구라서 Node에서 직접 부를 수 없다. 그래서 Node가 계산하고, Claude가 도구를 부른다.
    1. ArtifactData `get meta/head`로 버전을 확인한다. `list blocks`는 `out_dir`로 파일에 저장한다.
    2. `node jobs/picklog.js step`
       - 그 시각을 기준으로 레코드 본문을 다시 만든다. 마감이 지난 것은 뺀다.
       - `jobStep`(P8)으로 다음 동작을 정하고, 블록 JSON 파일과 batch 명세를 쓴다.
    3. ArtifactData `batch`
       - 각 항목은 `file_path`로 넘긴다. 해시가 든 블록을 손으로 옮겨 적지 않는다.
       - 머리 문서는 `if_version`으로 고정한다.
    4. 버전 충돌이면 1부터 다시 한다(최대 6회). 대시보드 잠금이 살아 있으면 만료까지 기다린다(최대 90초).
  - **마감 소급 금지:** 재시도할 때마다 그 시각으로 레코드를 다시 만든다.
    - 마감이 지난 평가·픽·2폴더는 빼고 "마감 경과, 기록 안 함"으로 보고한다.
    - 대시보드도 같다. 마감 뒤 입력은 배당 검증에서 거부된다.
  - **실패는 조용히 넘기지 않는다**
    - 일일 실행: 실패 사유, 영향받은 마켓, 마감 경과 여부를 아래 다섯 곳에 남긴다.
      - 실패 사유의 예: 잠금 대기 초과, 버전 충돌 재시도 소진, 체인 불일치, 도구 오류, 권한 거부, 승인 대기
      - (1) 리포트 맨 위 빨간 줄
      - (2) 대시보드 머리글 경고(`today.json`의 `alerts`)
      - (3) git 실행 기록 `data/runs/2026-27/{ET날짜}-{A|B}.json`
      - (4) DB `runs/{runId}`(쓸 수 있을 때)
      - (5) 예약 작업 완료 알림(휴대폰 푸시)
    - 대시보드
      - 쓰기에 실패하면 머리글 아래에 고정된 빨간 띠를 띄운다(사유, 시각, 마켓).
      - 입력 내용은 폼에 남겨서 마감 전에 다시 시도할 수 있게 한다.
      - DB의 체인 밖 문서 `failures/{id}`에 실패 기록을 남기려고 시도한다. 다음 일일 실행이 이것을 읽어 리포트에 싣는다.
      - `failures/` 쓰기마저 실패하면 화면 띠가 유일한 기록이라고 띠에 적는다.
  - **첫 실제 DB 쓰기 확인(조건 7)**
    - 첫 쓰기 뒤에 다시 읽어 체인 검증 결과와 내용(종류별 개수, seq, 해시)을 보고한다.
    - 확인 대상은 첫 `runs` 문서(첫 실행)와 첫 체인 레코드(아마 사용자의 첫 배당 입력) 두 가지다.
    - 첫 체인 쓰기 다음 실행의 리포트에 "첫 체인 쓰기 확인" 칸을 넣는다.
  - **소유자 권한:** 권한 시험용 쓰기(`as_level` 쓰기 포함)로 확인하지 않는다. STATUS.md에 미검증 항목으로 남긴다.

- **5. git 커밋 (조건 10)**
  - 푸시할 브랜치: `main`(기본 브랜치). fast-forward만 한다(결정 3).

    - `verifyChain`이 정상이다.
    - 앞서 커밋한 `log.jsonl`이 새 사본의 앞부분과 바이트 단위로 같다.
    - 하나라도 실패하면 사본과 `anchor.json`을 커밋하지 않고, 리포트·대시보드·알림으로 경고한다.
  - 사본 형식: 레코드 한 줄에 하나, 키를 정렬한 JSON(해시 계산과 같은 정규화). DB가 키 순서를 바꿔도 비교가 흔들리지 않는다.
  - `anchor.json`: `{count, seq, hash, commit}`
    - `commit`은 사본을 커밋한 커밋 해시다. 그래서 anchor는 다음 커밋으로 넣는다.
    - 빈 체인이면 `count: 0`이고, 대시보드는 "git 기준점 일치 — 레코드 0개"로 표시한다. 지금 `anchorCheck`는 seq만 보므로 빈 체인 처리를 더한다.
