# 자동 경고 기준값 등록 — runEarly · missedRun · finalZero · evalZero (2026-11-13)

- 근거: 2026-11-13 사용자 결정 "[11-11 ET A·B 보고 검토 / 결정]" 5
- **이 문서는 구현 전에 등록한다. 등록한 기준값은 뒤에 완화하지 않는다.** 더 엄하게 바꿀 때도 먼저 묻는다.
- **2026-11-13 개정(사용자 결정 "[11-12 ET 보고 검토 / 결정]" 6, 구현 전):** 모두 더 엄하게 바꾼 것이다.
  - runEarly: 180분 상한을 없앴다. 5분 이상 이르면 모두 잡는다.
  - runEarly·finalZero: "2회/2일 연속에 푸시"를 없애고 **첫 회부터 푸시**한다. 근거는 아래 각 절의 "연속 조건을 없앤 이유" 한 줄이다.
  - evalZero는 바꾸지 않았다. 판정 대상을 분명히 하는 안은 6절에 제안으로만 적었고, 승인 전에는 구현하지 않는다.
- **경고만 낸다.** 예측, 최종·예비 판정, 평가, 픽 로그 레코드는 바꾸지 않는다.
- 경고는 기존 방식을 그대로 쓴다.
  - 실행 기록의 `alerts`에 남는다.
  - 대시보드 머리글에 경고 칩이 뜨고, 연속 경고면 `escalated`·`streak`이 붙는다(`engine/run-alerts.js`).
  - `prepare` 출력의 `push`에 문장이 들어간다. A·B·C 지시문 1단계가 그 문장을 PushNotification으로 보낸다.
- 시각 기준
  - 실행 기준 시각 `runAt(run, etDate)`: A 17:50 ET, B 20:50 ET, C 07:50 ET(`engine/trigger-time.js`)
  - 실행 시작 시각: 실행 기록의 `startedAt`

## 1. runEarly — 기준 시각 전에 돈 예약 실행
| 항목 | 값 |
|---|---|
| 대상 | 실행 A·B·C. 수동 실행(`--manual` 인자)은 제외 |
| 조건 | `runAt − 시작 시각`이 **5분 이상** (상한 없음, 2026-11-13 개정) |
| 1회 | 경고(칩)와 **푸시**. 문구: "실행 X가 기준 시각(HH:MM ET)보다 N분 일찍 돌았습니다. 예측은 예비입니다. 예약 시각(서머타임)을 확인하세요" |
| 2회 연속 | 같은 실행 종류에서 이어지면 `escalated`·`streak`을 붙인다(푸시는 1회부터) |
| 경고하지 않음 | 기준 시각 뒤 시작(정상 지연, 몇 분~몇 시간 늦어도 이 경고는 아님). 5분 미만 이른 시작 |

- ~~180분을 넘게 이른 실행은 예약 실행으로 보지 않는다.~~ (2026-11-13 삭제)
- 연속 조건을 없앤 이유: 이른 실행은 첫 회에 이미 그 실행의 예측을 모두 예비로 만든다. 그래서 둘째 회를 기다리면 하루치 손실만 늘어난다(11-01 사례에서 첫 경고가 하루 늦어진다).

## 2. missedRun — 빠진 실행 (교차 확인)
| 실행 | 확인하는 직전 실행 |
|---|---|
| A (ET 날짜 d) | 전날 B(ET d−1)의 실행 기록, 당일 C(ET d)의 실행 기록 |
| B (ET 날짜 d) | 당일 A(ET d)의 실행 기록 |
| C (ET 날짜 d) | 당일(KST) A·B, 즉 ET d−1의 A·B 실행 기록 |

- 기준: `data/runs/<season>/<ET 날짜>-<실행>-*.json`이 그 실행의 checkout(main)에 없으면 빠진 것이다.
  - 경기가 없는 날이나 B의 "대상 없음"에도 실행 기록은 남는다. 그래서 그런 날도 기록이 있어야 정상이다.
- 1회부터 경고하고 푸시를 보낸다.
- 확인 범위는 바로 앞의 정해진 실행뿐이다. 여러 날이 빠졌으면 빠진 실행 목록(최대 9개)을 문구에 넣는다.
- 시즌 첫 실행처럼 비교할 직전 실행이 없으면 경고하지 않는다.

## 3. finalZero — 최종 예측 0건
| 항목 | 값 |
|---|---|
| 대상 | 실행 A·B |
| 조건 | 그 실행의 그룹 경기가 1개 이상(A는 A 그룹, B는 B 그룹)인데, 그 그룹의 최종 예측이 0건 |
| 1회 | 경고와 **푸시**. 대시보드 칩 문구는 "시각 오류 의심" (2026-11-13 개정) |
| 2일 연속 | 같은 실행 종류에서 이어지면 `escalated`·`streak`을 붙인다(푸시는 1회부터) |
| 세지 않음 | 그 그룹 경기가 0개인 날(경기 없는 날), B의 "대상 없음" 실행. 연속 판정에서도 건너뛴다 |

- 연속 조건을 없앤 이유: 제시간에 돈 실행은 시작 전인 그룹 경기를 모두 최종으로 만든다(`isFinalRun`). 그래서 그룹 경기가 있는데 최종이 0건이면 하루만으로도 시각 오류나 결함이다. 정상인 하루가 이 조건에 걸리는 경우가 없다.

## 4. evalZero — 입력 배당이 있는데 평가 0건
| 항목 | 값 |
|---|---|
| 대상 | 실행 A·B·C의 픽 로그 단계 |
| 조건 | 이 실행 경로에서 평가할 수 있었던 대기 배당이 1개 이상인데 평가 레코드가 0건. 평가할 수 있었던 배당은 경로가 맞고 마감이 실행 시각 + 여유 2분보다 늦은 배당이다 |
| 1회 | 경고. 대기 사유를 `notes`에서 가져와 함께 적는다 |
| 2일 연속 | 승격하고 푸시를 보낸다 |
| 세지 않음 | 대기 배당이 0개인 실행(배당 입력이 없는 날) |

- 픽 로그 단계는 `prepare` 뒤에 돈다. 그래서 이 경고는 `picklog plan` 출력의 `notes`에 넣고, 실행 기록에 `mark` 단계로 남긴다. 다음 실행의 승격 판정이 이 기록을 본다. 지시문은 바꾸지 않는다.

## 6. evalZero 판정 대상 — 제안 (승인 전 구현하지 않음, 2026-11-13)
- 문제: 4절 조건을 글자대로 쓰면 실행 A가 B 그룹 경기의 AB 경로 배당을 "평가할 수 있었던 배당"으로 센다.
  - A의 B 그룹 예측은 언제나 예비라서(`isFinalRun`), A는 그 배당을 평가할 수 없다. 그 배당은 B가 평가한다.
  - 그래서 B 그룹 배당만 입력된 날마다 A에서 evalZero가 나고, 2일이면 푸시가 간다(오경보).
- 제안: "평가할 수 있었던 배당"에 **그 실행이 최종 예측을 내는 경기의 배당**이라는 조건을 더한다. A는 A 그룹, B는 B 그룹, C는 C 경로 배당의 경기 전부다.
  - 이 조건은 경고가 나는 경우를 줄이므로 완화에 해당할 수 있다. 그래서 먼저 묻는다.
- 연결(지시문 변경 없음)
  - 판정은 6단계 `report --chain D`에서 한다. 이때 D에는 이 실행이 쓴 평가 레코드까지 들어 있다.
  - 경고는 그 실행의 리포트와 실행 기록에 남는다.
  - 대시보드 칩과 푸시는 **다음 실행의 1단계**(`prepare`)에서 나간다. 지시문 1단계만 푸시를 보내기 때문이다.
  - 같은 실행에서 푸시하려면 지시문 6단계 뒤에 푸시 줄을 더해야 한다. 그 안은 제안하지 않는다.
